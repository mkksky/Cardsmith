# 写法规范

字段名、格式、语法限制见 `CARD-SPEC.md`。这份文档只管**怎么写才有效**。

目标只有一个：**让技能在下次该用它的时候真的被触发、真的被执行到位。**

---

## 一、description —— 唯一决定触发的东西

这是整张卡片里最要紧的字段。**正文写得再好，description 写错，技能永远不会被加载。**

### 结构

```
【做什么 + 关键特征】+ 当用户【什么场景】时使用。触发词：xxx、yyy、zzz
```

### 好的例子

```yaml
description: >-
  按分层架构约束代码的依赖方向：只允许外层依赖内层，阻止内层反向引用外层
  （如 domain 引用 infrastructure），并输出完整的违规导入链路。
  当项目有分层目录结构、需要防止架构腐化，或用户抱怨「检查一下有没有跨层调用」
  「依赖方向对不对」「分层乱了」「service 里直接写了 SQL」时使用。
  触发词：分层检查、跨层导入、依赖方向、架构约束、layer violation。
```

好在哪：先说做什么和怎么做的**特征**（输出完整链路），再说触发场景，最后把**用户可能说的原话**列进去 —— `service 里直接写了 SQL` 这种具体抱怨，比 `架构约束异常` 这种抽象说法更可能被真实说出来。

### 差的写法

| 写法 | 问题 |
|---|---|
| `用于提升代码质量` | 没有触发条件也没有具体能力，等于没写 |
| `这是一个很棒的调试助手` | 营销词。触发靠关键词，不靠形容词 |
| `处理各种构建问题` | 「各种」= 没有范围。什么构建？什么症状？ |
| `Root Cause Analysis Protocol` | 纯英文标题，中文提问时匹配不上 |

### 硬要求

- **单段**，长度 60 ~ 250 字。宁可长一点也要把触发词写全，超 400 字会 warn
- 中英文触发词**都写**（`构建失败 / build failed`）
- **把症状写进去**，不只是能力。`hook 没执行` 是症状，`配置 hook` 是能力
- 不用「如果…的话可以使用」这种软措辞，直接写「当用户…时使用」

## 二、正文结构

正文会成为生成后的 SKILL.md 正文。六节，**全部可选**，但每删一节都要能说出为什么。

| 小节 | 该写什么 |
|---|---|
| 何时使用 | 具体触发场景，能被一眼比对 |
| 核心方法 | **为什么**这么做、不这么做会怎样、边界在哪 |
| 常见坑 | 表格：坑 / 症状 / 解法。只写真实踩过的 |
| 实施步骤 | 有序操作。步骤间有依赖就明说 |
| 验证 | 可观测判据：退出码、文件存在、计数对比 |
| 注意 | 零散但重要的约束 |

### 判定标准

每写一节，问一句：**这节会让下次执行时的我做出不同的动作吗？**

不会，就删。这条标准能砍掉 80% 的注水内容。

### 「常见坑」为什么必须有症状列

下次遇到同一个问题时，**先看到的是症状，不是原因**。症状列让技能能被「倒着检索」—— 从现象反查解法。只写原因的坑表，出问题时用不上。

### 「验证」为什么不能省

如果没法判断"这次真的做完了"，技能就只是一份建议书。判据必须是**可观测的**：命令退出码、文件存在与否、计数变化。

「看起来没问题」不是判据。

## 三、什么时候该写 tools/

满足任意一条就写脚本：

- 有一段逻辑会被反复执行，且手抄容易错（参数顺序、路径拼接、编码）
- 需要「跑一次拿到结果」而不是「读一段理解」
- 逻辑里有平台差异（Windows / Unix 路径、解释器探测）

要求：

- **纯标准库优先**。环境没装好不该让技能整体失效
- `pathlib` + 显式 `encoding="utf-8"`，不靠平台默认编码
- 支持 `--selftest`，改完先证明自己没坏
- 退出码统一：`0` 通过 / `1` 有违规 / `2` 配置错误
- 在卡片里登记完整契约（入参、输入来源、退出码含义）

**注意**：卡片声明了 tool 但脚本不存在，`check.py` 会直接报错。这是刻意的 —— 「文档说有，实际没有」正是这套东西要消灭的状态。

## 四、什么时候该写 rules/

规则细节动辄几十行（比如分层依赖矩阵），塞进卡片 frontmatter 会让卡片没法读。

判断标准：**这段内容需要被机器逐字段读取吗？**

- 需要 → 写 `rules/*.json`，卡片里用 `source` 引用
- 只是给人看的说明 → 写在正文里

JSON 的选择理由不是它好看，是它**解析零歧义**。规则是程序执行的，不该冒解析风险。

## 五、反面清单

- **概念科普**：讲历史、讲原理、讲「什么是 X」。技能不是教程
- **抄官方文档**：官方文档会更新，抄进来的会过期。写链接和判断标准
- **无依据的礼貌建议**：`如果遇到问题请仔细检查代码` —— 零可执行信息
- **通篇「怎么做」没有「为什么」**：下次执行时无法判断何时该破例
- **没有验证节**：无法确认是否真的完成
- **绑定关系写两遍**：正文里手写「绑定了哪些工具」会和卡片打架。这部分由 `build.py` 自动派生

## 六、什么时候不该建卡片

- **只做过一次、不会重复的任务** —— 记到当天的工作日志就够
- **纯知识查询**（某个参数的含义）—— 直接查文档
- **找不到可绑定的检查工具** —— 见下

### 特殊：没有工具的技能，要想清楚再建

这套件的核心约束是「每个技能必须绑定可执行的检查」。所以纯方法论的技能（比如「怎么和老代码相处」）会卡在这里。

两种情况：

1. **确实能自动化** → 先写工具，再建卡片
2. **本质上是判断，无法自动化** → 可以建，但要在卡片里明确 `tools` / `hooks` 为空，且接受它只是一份清单、不享受门禁保护

**不要为了凑数硬塞一个假工具** —— 那比没有工具更糟，它会让 `check.py` 通过，同时给你一个"有检查"的错觉。

## 七、提交前自检

```bash
python scripts/build.py     # 卡片 → 生成物
python scripts/check.py     # 三方对账
```

脚本能查：字段合法性、tool 脚本是否存在、规则源文件是否存在、生成物有没有漂移、tool id 有没有冲突。

脚本查不出、要人看的：

- [ ] description 里的触发词，是用户真会说的原话吗？
- [ ] 每一节都能通过「会让下次的我做出不同动作吗」这一问？
- [ ] 「常见坑」每条都有症状吗？
- [ ] 验证节是可观测判据，而不是「看起来没问题」？
